# ops-desk — pipeline & data-freshness health monitor (session 54a39029)

**Task O-1** on the coordination board. This desk monitors the monitors: the dashboard's
"live" promise depends on GitHub Actions data pipelines, so this page inventories every
workflow, audits what actually ran from the official GitHub REST API, measures how fresh
each committed data tree is, and publishes reliability irregularities with evidence.

Everything here is **additive and self-contained**: no other session's files were edited.
Change requests for files owned by other sessions are logged on the board (see
`COORDINATION.md`, section "Session arena/54a39029-demo1").

## How the evidence is produced

1. `build_health.py` lists all workflows from the official API
   (`GET /repos/{owner}/{repo}/actions/workflows`), samples the 30 most recent runs per
   workflow (`GET .../workflows/{id}/runs`), pulls a 200-run repo-wide sample
   (`GET .../actions/runs`), and takes the last commit per monitored data path
   (`GET /repos/{owner}/{repo}/commits?path=...`).
2. Declared triggers are parsed **from the workflow files as shipped on `main`** (regex,
   no PyYAML), so "declared" vs "observed" can be compared honestly.
3. Expected cron starts in the sample window are plain arithmetic (`window_minutes / step`)
   and are always labelled *computed*, never presented as observed runs.
4. Nothing is inferred: a workflow with no runs is recorded as "no runs observed"; a path
   with no commits is recorded as such.

Official sources used (verified by fetching the pages):

- `schedule` trigger semantics — delays/drops under high load, default-branch-only, 5-minute minimum:
  <https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule>
- Workflow-runs endpoints (usable unauthenticated for public resources):
  <https://docs.github.com/en/rest/actions/workflow-runs?apiVersion=2022-11-28>
- Commits endpoints (same public-resource rule; `path` filter documented):
  <https://docs.github.com/en/rest/commits/commits?apiVersion=2022-11-28>

The browser "live re-check" reads the same endpoints unauthenticated; the committed
`data/cors-probe.json` documents the observed `access-control-allow-origin: *` headers.

## Run it

```bash
python3 ops-desk/tools/build_health.py      # refresh evidence (needs outbound api.github.com)
python3 ops-desk/tools/cors_probe.py
node ops-desk/test_ops_desk.mjs             # schema + DOM boot + live-check paths (uses jsdom)
node tools/check-links.mjs                  # repository link/hygiene checker
```

The page is static: it renders `data/health.json` relative to itself, so it works on
GitHub Pages exactly as committed. The live re-check is optional and always degrades
back to the committed evidence on failure.

## Flagged irregularities (also published on the page; non-blocking)

- **OPS-01** — `.github/workflows/sim-strategies.yml` shipped with **no** schedule trigger,
  although its board record (COORDINATION.md, S-4, line 1223) claims "on push + 30-min
  schedule". Full git history of the file contains zero `cron` lines. Consequence: the
  sim-desk simulated-trading ledger has only advanced when pushes touched `sim-desk/**`
  (last evidence: 2026-11-20T13:40Z, i.e. ~6 h idle at build time). Change request logged
  for the owning session (`9dcbe7d4`); not applied from this branch.
- **OPS-02** — Scheduled data pipelines rarely fire: in a 200-run repo sample over ~6¼ h,
  exactly 2 `schedule`-event runs were observed (~84 starts would be expected across the
  four `*/15`–`*/30` cron workflows, computed). One of the two observed runs was cancelled
  (concurrency). This matches the official schedule docs' high-load caveat ("some queued
  jobs may be dropped"). Consequence: committed data trees can go stale for hours;
  the freshness table above quantifies it per path.
- **OPS-03** — Pages deploy starvation: `pages.yml` uses concurrency group `pages` with
  `cancel-in-progress: true`. During merge storms every new merge cancels the previous
  deploy, so the published site can stay frozen while merges continue (evidence: the
  recorded run history — several consecutive `cancelled` runs with the last success lagging
  the repo state). Change request for the workflow owner: serialize with
  `cancel-in-progress: false` (queue instead of cancel) or route deploys through a single
  final integration session, so the site converges to the latest `main`.
