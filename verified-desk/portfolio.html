Portfolio & trades

Everything needed to track and analyse the demo account — endpoints, signing, order lifecycle, guardrails, ledger schema — plus a replay simulator that works without an account.

Nothing was executed, and that is not an oversight

Executing trades and reading a portfolio both require an API key pair registered to a demo account. This project has none: no key id and no private key were supplied, and none can be created without logging in to demo.kalshi.co. Rather than fake a balance or invent fills, this page states the exact call sequence, ships a tested signer reference, and leaves the account tables empty with a reason.

Unblocking is one decision: Q-1. The site then needs a place to keep the key — page code cannot hold it (see S-2).

Signing, exactly as documented

  • Keys are asymmetric: Ed25519 (default, recommended) or RSA-2048. Sign timestamp + HTTP method + path; Ed25519 signs the string directly, RSA uses RSA-PSS with SHA-256, MGF1-SHA256, salt length = digest length. Base64 the result.
  • Headers: KALSHI-ACCESS-KEY (key id), KALSHI-ACCESS-TIMESTAMP (milliseconds), KALSHI-ACCESS-SIGNATURE.
  • Sign the path without the query string but including the API root: /trade-api/v2/portfolio/balance.
  • The timestamp must be within 30 seconds of Kalshi's clock or you get 401 header_timestamp_expired even with a correct signature — keep NTP on.
  • Create a key on the host whose data you are trading: demo.kalshi.co/account/profile for this project, or kalshi.com/account/profile for production — or POST /api_keys/generate. The private key is shown once and is not retrievable afterwards. Production caps directly-managed keys at 100; the demo limit is not documented.
  • Reference implementation and its self-test: python3 tools/kalshi_sign.py --self-test — reproduces the RFC 8032 Ed25519 test vectors, then checks that the payload signed is timestamp + METHOD + path with the query string dropped. No network and no real credentials are involved, which is why the tool is trusted for the algorithm but still unproven against Kalshi's verifier (FL-7).

Order lifecycle the tracker must follow

POST /portfolio/events/orders
{
  "ticker": "KXAAAGASM-26DEC31-3.30",
  "side": "bid",
  "count": "1",
  "price": "0.0100",
  "time_in_force": "good_till_canceled",
  "self_trade_prevention_type": "taker_at_cross",
  "client_order_id": "strat:longshot-decay|topic:gas-prices|role:taker|1"
}
→ 201 { order_id, remaining_count }   # accepted, NOT yet resting
→ GET  /portfolio/orders/{order_id}    # may 404 briefly after the write
→ amend / decrease / DELETE            # Write bucket
→ fills, then settlements              # ledger closes the loop

Payload shape is quoted from the official quick start (create your first order). client_order_id is ≤64 chars of letters digits _ - : + = /, is unique per subaccount on the market's shard, and its duplicate rejection is 409 order_already_exists — which does not return the original order, so store it locally.

Guardrails this project commits to before any live order

  1. Order size capped at 1 contract, and only on the demo host, until a written go-ahead exists in the decision log.
  2. The depth gate from S-5: if the ladder cannot absorb the order within price_ranges, the button stays disabled — the UI on Price & liquidity already computes it.
  3. client_order_id carries the strategy tag and a UUID, so retries are idempotent and every fill is self-classifying.
  4. Private key never in the repository, never in page code, never in localStorage; only in the proxy's environment.
  5. Every order written to the ledger with the top-of-book snapshot taken at submission, so slippage is attributable later.
  6. An order group as an automatic brake on a runaway loop (rolling 15-second limit).
