Executive summary

Prepared 2026-11-20 from live reads of the Kalshi demo API and the official documentation. Written so that every number can be clicked through to its source, and every gap says who has to close it.

The one thing to know first

The market-data half of this brief is built and working against live demo data: collection, topic filtering, dollar-volume ranking, resolution tracking, price charts and liquidity depth. The account half is not, and could not be: no demo API key or private key exists in this project, and Kalshi requires a signed request for every portfolio read and every order. So no trades were executed and no portfolio was tracked — that work is designed, documented and unit-tested, and blocked on one credential from you (see Q-1).

2 · What the demo API actually is findings that change the plan

F-1 · There is no “dollar volume” field, so ranking is arithmetic we own

Markets report volume_fp, volume_24h_fp and open_interest_fp as fixed-point contract counts. Nothing in Get Markets reports dollars. This site therefore computes Σ volume_fp × last_price_dollars, labels it estimate, and flags any event whose legs were not fully captured as a floor. Exact turnover is recoverable — sum price × count across GET /trades — which is S-1.

F-2 · Volume in demo is thin enough that liquidity, not price, is the real constraint

In the captured set, the busiest US gas strike had 385.82 lifetime contracts and only 20.14 in 24h (event total $115.75 estimated, of which $111.89 is that one strike and the other four legs add $3.85); the three Ryder Cup legs had 1.17–1.18 contracts each; and 13 of the 20 captured legs printed bid 0.0000 / ask 1.0000 — no executable quote at all. Meanwhile KXBTC15M shows 7,949,039 contracts across the series. A strategy that ignores the book will look fine on paper and fail on the screen — hence the depth gate in S-5.

F-3 · Resolutions are observable to the second, and fast

Crypto 15-minute markets closed at 11:00:00Z and carried settlement_ts 11:00:04.609813Z with result: "no" and settlement_value_dollars: "0.0000". That is the whole “track until resolved, and how” requirement satisfied from one field set, on a cadence short enough to watch live. Golf showed the opposite extreme: The Open legs settled within minutes of the final putt, and the rules_secondary text explains the fair-market-price branch for a golfer who never tees off.

F-4 · Event status ≠ market status, which is the trap in this design

The California ballot event was returned by status=open even though three of its four markets were already finalized, because one leg was still active. Any tracker that polls events and marks them done on the first settlement, or that trusts event status alone, will mis-report. The tracker here therefore counts settled legs against total legs.

F-5 · The API returns empties in three different shapes

An unknown tags value on GET /series returns {"series":null}; a closed or mistyped order book returns 200 with empty arrays and never 404 (documented in Orderbook Responses); and GET /series silently ignores limit. Naive dashboards render these as zeros. Here “no data” prints — and “real zero” prints 0.00.

F-6 · Fees are steep at mid prices and trivial at the tails — which shapes strategy

The published taker formula 0.07 × C × P × (1−P) peaks at $1.75 per 100 contracts at 50¢ and falls to $0.07 at 1¢ or 99¢ (the engine reproduces all 21 rows of the official table in tests). Consequence: mid-price churn is expensive, longshot/favorite harvesting is nearly fee-free, and maker pricing (0.0175) only exists where the series enables it — KXAAAGASM runs maker 1 / taker 1, so the gas ladder has no maker rebate.

F-7 · Demo is not a small production; it is a different catalog

The docs warn that demo prices and behaviour “may not be reflective of those in real markets”. Concretely: the Culture category contains exactly two series, both with zero volume, and there is no “Election” tag (GET /series?tags=Election returns {"series":null}) — elections live in a separate Elections category. Any conclusion about “culture markets” from demo is an artefact of the sandbox, so S-6 asks for a production reconciliation run before decisions are made.

F-8 · A static site is the right shape for 80% of this, and structurally wrong for 20%

Public REST reads are unauthenticated and cacheable, so GitHub Pages can serve the whole market-data experience with no server. Portfolio reads, order writes and the WebSocket handshake all require signed headers; a browser cannot attach headers to a WebSocket at all, and embedding a private key in page code would leak it. So the architecture is: static site + optional live fetch + one tiny signed proxy when you want account features (S-2).

4 · Recommended path sequenced, with the decision each step unlocks

Phase 0 — decide three things (this week, no engineering)

  • Demo or production data as the source of truth? The brief says demo; demo is thin (F-2, F-7). Recommendation: keep demo for plumbing and executions, and rank topics off production public data, which needs no credentials at all.
  • Issue a demo API key? Answering Q-1 unblocks portfolio tracking, fills, orders and the WebSocket. Everything else is already built.
  • Accept the dollar-volume proxy, or pay for exactness? Accepting it keeps a static site; exactness means summing trades (S-1).

Phase 1 — make the live path real (1–2 days)

  • Run the browser live scan once and record whether the demo host answers cross-origin; if it does not, that is the only reason to build a proxy for market data. (FL-2)
  • Add scheduled snapshot refresh into git so every published number carries a timestamp (S-7).
  • Wire the resolution poller for markets inside their close window (S-9).

Phase 2 — account features (needs Q-1)

  • Deploy the signed proxy; read balance, positions, fills; write the ledger into the same tables that already exist here.
  • Stamp strategy ids into client_order_id from day one, or the categorisation you asked for will be unreconstructable (S-4).
  • Only then place orders, starting with the deepest series (KXBTC15M) at 1 contract, with the depth gate from S-5 refusing anything the book cannot absorb.

Phase 3 — decision support

  • Sub-second charts via the authenticated WS feed; alerts on settlement rather than price; strategy evaluation over stored fills rather than over a 20-row snapshot.

5 · Verification statement

  • Sources. Only docs.kalshi.com, the kalshi.com fee PDF, and the demo API itself were used for claims. Third-party articles were used only as a lead to find candidate series tickers, and every ticker taken that way was then confirmed against the API before appearing anywhere in this repo. That provenance chain is recorded per row in data provenance.
  • Tests. node --test tests/kalshi.test.mjs → 34 passing, covering money rounding, the fee table, classification precedence, resolution edge cases, book walking, candle range validation and the null-vs-zero rules.
  • Reproducibility. tools/refresh_snapshot.py regenerates the snapshot with the same schema from any machine with network access; tools/check_links.py verifies every outbound link returns 200. Both are documented as untested in the agent sandbox, because the sandbox has no egress to Kalshi (see FL-7).
  • Not verified, deliberately. CORS reachability from a browser, the exact market status enum, rate-limit tier numbers for this account, and anything requiring an API key. Each is blank + flagged instead of filled in.

Standing caveat

Kalshi's own documentation states that demo prices and behaviour may not reflect real markets, and that demo uses mock funds. Nothing on this site is investment advice, and nothing on it has moved money.
