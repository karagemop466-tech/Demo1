Questions, information & answers required before decisions

A decision can only be made from information we actually have. This page separates the three states explicitly: ANSWERED (verified against an official source, linked), UNKNOWN (cannot be answered from available information — the missing data is named), DECISION NEEDED (facts exist but a reviewer must choose). Suggestions for discovering missing information are embedded in each entry and rolled up at the bottom.

Rule applied throughout: if a value cannot be confirmed from an official source it is left blank and flagged — never inferred. See Flagged for Review and verification log.

The questions

Q1 · What exactly is the “highest dollar amount” used to rank live events?
Information we have (official): the Market schema publishes volume_fp, volume_24h_fp, open_interest_fp (contracts) and notional_value_dollars — but no dollar-volume field (Get Markets).
Current default: rank by computed 24h dollar volume = volume_24h_fp × last_price_dollars, with the other two metrics side-by-side on the dashboard.
Missing: the business definition you want. What resolves it: pick one metric in the dashboard “Rank by” toggle and record it as the standard (suggestion C3).
UNKNOWN
Q2 · Does the demo API allow direct browser (CORS) calls?
Information we have: nothing official — the documentation does not mention CORS, and the build sandbox cannot reach kalshi hosts to inspect response headers.
Missing: Access-Control-Allow-Origin behavior for browser origins.
What resolves it: open dashboard.html and read the connection badge (LIVE / relay / BLOCKED), or ask Kalshi support to confirm. Until then: UNVERIFIED-01.
Suggestion to discover: C1 — treat transport as the first blocking decision.
UNKNOWN
Q3 · Where do demo API credentials come from, and who provides them?
Information we have (official): demo accounts live at demo.kalshi.co; keys are created per account and never shared between demo and production (demo env · API keys).
Missing: an actual key pair. Credentials must never be posted in chat; they are entered only into trades.html → Settings (localStorage).
What resolves it: a reviewer creates a demo key and pastes it locally. Until then all authenticated cells stay blank: UNVERIFIED-02.
ANSWERED
Q4 · Is demo data the same as production data?
Official answer: no. “The price and behavior of markets in the demo environment may not be reflective of those in real markets.” (source). Consequence: every figure on this site is demo-environment data by requirement — UNVERIFIED-05. No decision required unless you later want production data (out of scope for this brief).
ANSWERED
Q5 · How does an event resolve — how do we know YES vs NO?
Official answer: markets move through lifecycle statuses initialized → inactive → active → closed → determined → (disputed) → finalized; the Market result field then holds yes, no, scalar or empty (schema). Yes holders are paid $1/contract on a Yes outcome, No holders $1/contract on a No outcome (settlement). This site: markets.html polls open markets and logs every observed result into the resolution watch log.
DECISION NEEDED
Q6 · Is client-side sampling acceptable for the “seconds” chart?
Information we have (official): candlesticks exist only at period_interval 1, 60 or 1440 minutes (docs) — there is no official seconds series.
Current default: sample GET /markets/{ticker} every 2s in the browser and plot the mid price (labeled, UNVERIFIED-07).
What resolves it: accept sampling, or choose authenticated WebSocket ticker streaming (suggestion C5) for true tick data.
DECISION NEEDED
Q7 · How should the five topics (gas, elections, culture, crypto, golf) be identified?
Information we have: GET /series supports an exact, case-sensitive category filter, but the list of valid category strings is not published (docs).
Current default: transparent keyword classifier over series title/ticker/category/tags — the keyword list and matched series are displayed on markets.html (UNVERIFIED-06).
What resolves it: reviewer confirms the matched series look right, or supplies official series tickers per topic.
DECISION NEEDED
Q8 · Should performance include fees?
Information we have (official): fee structures are per-series (fee_type, fee_multiplier) and documented in the fee schedule; settlement fees are zero for simple yes/no outcomes (settlement).
Current default: paper P&L excludes fees and says so on the trades page.
What resolves it: accept fee-free estimates (fast) or implement fee-aware P&L (suggestion C7, more faithful).
DECISION NEEDED
Q9 · What is the paper-trading bankroll / risk budget?
Information we have: none — no budget was specified anywhere in the brief, and the site must not invent one.
Current behavior: paper trades have no cap; cost basis is simply count × price.
What resolves it: a reviewer sets a budget (e.g., $1,000 simulated) and a per-trade cap; suggestion C6 can attach position sizing to strategy tags.
DECISION NEEDED
Q10 · Is the third-party relay acceptable while CORS is unresolved?
Information we have: if the browser blocks direct calls, requests can be forwarded through a public relay while still targeting the official API URL — but a third party sees the traffic (UNVERIFIED-03). Toggle exists in trades.html → Settings.
What resolves it: accept (default, data is public market data), or disable and live with blank values until C1 is done.

Q11 · Which hosts does this site talk to?
Official answer: demo REST https://external-api.demo.kalshi.co/trade-api/v2 (recommended) with https://demo-api.kalshi.co/trade-api/v2 as alternate; demo WS wss://external-api-ws.demo.kalshi.co/trade-api/ws/v2 / wss://demo-api.kalshi.co/trade-api/ws/v2 (source) — exactly the endpoints in the project brief. The code hardcodes demo hosts; production hosts are never called.

Q12 · Which order parameters should execution use by default?
Information we have (official): Create Order V2 requires side (bid/ask), count, price, time_in_force (fill_or_kill | good_till_canceled | immediate_or_cancel) and self_trade_prevention_type (docs).
Current default: good_till_canceled + taker_at_cross, limit at best ask (taker) or best bid (maker) — selectable in the ticket.
What resolves it: reviewer confirms defaults or specifies maker/taker policy per strategy.

What resolves it: pick one primary metric; suggestions with conflicting rankings must then be ranked by it (feeds the path picker on suggestions.html).
