SEC-01 Real-order credentials are stored in browser local storage by the experimental exec-desk trade page. trade-exec.js reads and writes the private PEM under a local-storage key and exposes a real-order mode. This is not a safe credential boundary for a public static site; do not enter a private key there. A protected server-side signing service is needed before real account use. Open · use paper mode only Repository evidence ↗Kalshi API-key guidance ↗
AUTH-01 The experimental browser trade signer omits the documented /trade-api/v2 prefix from the signed path. authFetch sends to the demo base URL plus an application-relative path, while signedHeaders signs that relative path alone. Kalshi’s official signing example uses the full API path (for example, /trade-api/v2/portfolio/balance). No key was available, so this mismatch was not exercised against an account; authenticated execution must be treated as unverified. Open · correction requested; no account test Signer evidence ↗Official signing path ↗Official order endpoint ↗
KEY-01 The browser key importer appears not to accept the documented Kalshi-generated RSA private-key PEM format. pemToBuf strips only a generic PRIVATE KEY header and signedHeaders imports the bytes as PKCS#8. Kalshi’s API-key guide shows generated RSA keys with a BEGIN RSA PRIVATE KEY PEM header (PKCS#1); no credential was available to test this path. RSA-key import is therefore unverified and likely incompatible with the documented generated file. Open · format handling/test requested Importer evidence ↗Official key generation and formats ↗
PAPER-01 Closing a simulated YES position applies the wrong close-value expression. The position renderer passes a YES-market mark to closePaper, but the YES branch calculates proceeds using 1 − closePrice. This can make closed-paper P&L incorrect. Do not rely on closed YES results until the owner fixes the formula and adds a regression test. Open · correction requested Caller evidence ↗Calculation evidence ↗Official market price fields ↗
FILL-01 An accepted real-order response is copied into the local trade ledger using the requested quantity, even when the displayed fill count is zero or partial. trades.js displays resp.fill_count but then unconditionally creates a local ledger record from the original ticket quantity and price. Kalshi documents that order acceptance is not proof of a fill; until the ledger reconciles with official fills, its real-order mirror may overstate executed positions and P&L. Open · reconciliation/correction requested Ledger evidence ↗Official order acceptance behavior ↗Official fills endpoint ↗
JUMP-01 The jump scanner can stop accepting refreshes after a scan returns no qualifying jumps. In jumps.js, the no-results branch returns before resetting the scanning guard. Since later scans exit while that guard is true, a no-jump result can leave the page stuck until reload. Open · correction requested Repository evidence ↗Official candlesticks reference ↗
SCOPE-01 The direct live dashboard ranks a bounded, keyword-classified scan—not every market in the exchange. The current code reads a bounded number of series pages, selects a limited set of high-volume matched series for each topic, then requests a bounded event page. Results should be described as the scanned set, not as an exhaustive category census. The five-topic classifier is heuristic. Known limitation · keep disclosed Repository evidence ↗Official series endpoint ↗Official events endpoint ↗
RANK-01 The dashboard’s computed dollar ranking can substitute a quote when the last-traded price is missing. dollarVolume24h and the open-interest estimate call midPrice when last_price_dollars is absent. That helper can use a bid/ask midpoint or a single reported bid/ask. The dashboard text describes the last-price formula but does not disclose this fallback; these figures are estimates, not confirmed traded notional. Open · label/data rule correction requested Calculation evidence ↗Dashboard label ↗Official market price fields ↗
SIM-01 The automatic paper-strategy runner is on-demand and uses a fixed watchlist. The page evaluates predeclared strategies only after “Run engine” is selected; the current script lists ten event tickers. It is not a continuous, full-market autonomous trading service. Results persist in the current browser and must not be confused with demo-account fills. Known limitation · scope disclosed Repository evidence ↗Official markets endpoint ↗
LEGACY-01 The older root market-table order-book button references a variable outside its scope. In app.js, bookId is declared inside a mapping callback and later referenced from a separate click callback. The legacy root market pages are not used as the canonical live desk; keep them out of the primary navigation until corrected. Open · legacy path de-emphasized Repository evidence ↗Official order-book endpoint ↗
TEST-01 A previously reported mocked-fixture mismatch was not reproducible after rebasing onto the latest main. The current node --test tests/dashboard.test.mjs run passes all 46 assertions across pages/live.html, resolutions, strategy, and shared-engine behavior. The suite mocks network calls, so this pass is not evidence that the live API is reachable or that current exchange values match the fixtures. No other session's test or implementation files were changed. Rechecked · 46/46 pass; mocked coverage only Mocked test evidence ↗Tested dashboard page ↗Official public market-data guide ↗
