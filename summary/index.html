02 / Verified findings

What the official documentation establishes

The dollar question has an answer, but not the one that was asked for

Kalshi exposes open_interest_fp, volume_fp, volume_24h_fp and notional_value_dollars. A binary contract pays $1 on a winning outcome. That makes three defensible dollar measures: open-interest notional, 24-hour traded notional, and resting depth notional.

There is no published “highest dollar amount” ranking, and contract volume is not dollars. This site therefore names each metric and prints its formula rather than substituting one for another. Choosing the default ranking is a decision for a human — it is item 1 on the questions register.

Get Markets ↗ · Market Settlement ↗

Resolution is a documented lifecycle, and it is auditable

Markets move through initialized → active → closed → determined → finalized, with disputed and amended as the exception states. The result field becomes yes, no or scalar, and a settlement timer runs before payout.

Each event also carries its settlement sources, which is what makes a resolution checkable rather than merely reported. The events page shows status, result and settlement time side by side, and the ledger records what this project observed between captures.

Market Lifecycle ↗ · Get Events ↗

The order book answers the liquidity question directly

The book publishes bids only, on both the YES and the NO leg, as [price, contracts] pairs sorted ascending — so the best bid is the last element. The ask side is derived: a YES ask is $1.00 minus the best NO bid. A depth parameter returns the best N levels per side.

That is exactly the “how many contracts are available at a given price” question, so the liquidity page answers it per level with the dollar value resting at each price.

Orderbook Responses ↗ · Get Market Orderbook ↗

Seconds-resolution history is not on the server

The candlestick endpoint accepts period_interval of 1, 60 or 1440 minutes only. There is no sub-minute candle. A seconds view is therefore produced by sampling the live public quote in the browser, and the page says so rather than passing it off as an official series.

A true tick tape would need a signed WebSocket relay, because the Kalshi WebSocket API requires handshake headers that a browser cannot set. That is the single highest-value suggestion on the list.

Get Market Candlesticks ↗ · Quick Start: WebSockets ↗

Account access is signed, and it can stay in the browser

Signed requests need three headers, with the signature taken over timestamp + method + path using RSA-PSS SHA-256 or Ed25519, and a 30-second timestamp tolerance. This project signs in the browser with the Web Crypto API, so a private key never has to be uploaded to any server, and it is discarded when the tab closes.

The blocker is not technical: no Kalshi demo account exists for this project. The demo environment uses mock funds and its credentials are separate from production.

API Keys ↗ · Demo Environment ↗

The order endpoint moved, and the side is quoted on one leg

The legacy /portfolio/orders write endpoints now return 410 Gone; order entry is POST /portfolio/events/orders. Its side refers to the YES leg only: bid buys YES and ask sells YES, with selling YES economically equal to buying NO at 1 − price.

The trading ticket uses that endpoint, quotes the price on the YES leg and shows the equivalent NO price so a direction can never be misread.

05 / Architecture

How the site is built

Data layer

Refresh workflow

A scheduled GitHub Actions job pulls the demo API and writes data/*.json. The ledger is persisted through the Actions cache so events can be followed across captures. A best-effort step commits the snapshot back to the repository.

Data layer

Browser layer

Every page reads the snapshot first, then tries a live public REST request. If the browser can reach the API it wins and the header shows “live”; otherwise the header shows “snapshot” with its capture time. The two are never mixed inside one table.

Presentation

Static pages

Thirteen pages of plain HTML, CSS and ES modules with no framework and no third-party assets, so the site has no runtime dependency to break and no build step to get wrong.

Account layer

Browser-side signing

Private keys are imported into the Web Crypto API and used to sign locally. Nothing is uploaded, and the key lives in sessionStorage only.

Account layer

Automated runner

scripts/run-demo-trade.mjs places demo orders under a documented strategy with hard limits, and refuses to act unless trading is explicitly enabled and a key exists.

Quality

Verification

A site check validates every internal link and anchor and asserts that each data table carries a source link. The workflow runs it on every build.

Scope statement. Everything on this site runs against the Kalshi demo environment, which uses mock funds and whose prices and behaviour may not reflect real markets (official notice ↗). Nothing here is evidence of live profitability, and no order is placed without an explicit signed confirmation.
