Suggestions & Open Questions

A dedicated review section: the questions that must be answered — with what we know, what we don’t, and how to discover the missing information — before any decision is taken on the improvements proposed below. Nothing here is implemented without review.

A · Questions, information & answers needed before decisions

Format: Question → Known/answer (with sources) → Missing information → How to discover it. Items marked gating block the related suggestion.

Q1 · Which demo credentials will be used for real demo-account trade execution? gating
Known: demo accounts live at demo.kalshi.co with mock funds; API access requires an API key ID + Ed25519/RSA private key with signed requests (official auth docs). Missing: no demo credentials exist in this project (none were provided — correctly so; secrets must never be pasted into chat or a static site). Discover: (1) log into demo.kalshi.co; (2) create an API key in account settings; (3) store the private key only in a server-side secret store (see S1). Decision needed: approve S1 proxy or accept SIM-only portfolio.
Q2 · Can the browser call external-api.demo.kalshi.co directly (CORS)? gating
Known: the endpoint is the documented recommended demo host (API environments) and public market data needs no key (quick start). Official docs do not state CORS behavior for browser origins. Missing: whether Access-Control-Allow-Origin permits arbitrary origins for public GETs. Discover: open Live Markets on the published site and check the connection badge; or run curl -I -H "Origin: https://karagemop466-tech.github.io" …/markets?limit=1 and inspect headers. If blocked → S1 proxy (read-only variant) is required.
Q3 · Which exact series define “gas prices / elections / culture / crypto / golf”?
Known: candidate series are committed in data/series-map.json and verified at runtime via GET /series/{ticker} (200 = verified); anything unverified is excluded and shown on the Flagged page. Missing: the demo environment’s current market lineup changes daily — the authoritative list is only knowable live. Discover: click “Re-verify series map” on Live Markets (fresh GET /series checks), then review the pills per topic. Decision needed: confirm/remove any candidate you don’t want tracked.
Q4 · What does “highest dollar amount” mean precisely?
Known: Kalshi reports volume in contracts, plus open_interest and liquidity fields; there is no published dollar-volume field. The site sorts by Est. $ volume = Σ contracts × last price, clearly labeled an estimate. Missing: your preferred ranking metric. Discover: compare the columns side-by-side on Live Markets for a few days. Decision needed: keep Est. $ volume, or switch to contracts volume / open interest / liquidity.
Q5 · Demo vs production data — which should the tables show?
Known: demo markets are a sandbox subset with mock funds; production (external-api.kalshi.com/trade-api/v2) has the full, liquid market lineup. The brief specifies the demo environment, so all live reads use demo endpoints. Missing: whether you also want a read-only production view (demo volumes can be thin and some topics may have no open demo markets at times). Discover: watch Live Markets for a week; if tables are frequently empty for a topic, that is a demo-lineup issue, not a bug. Decision needed: add a clearly-separated production read-only toggle (S8) or stay demo-only.
Q6 · Portfolio scope — new trades only, or backfill history?
Known: authenticated endpoints (GET /portfolio/fills, GET /portfolio/settlements) expose fills and settlements once credentials exist (Q1). Until then the SIM ledger starts empty. Missing: whether to import the demo account’s pre-existing trade history once S1 is live. Discover: after S1, run GET /portfolio/fills and inspect the historical span available. Decision needed: backfill or start-from-now.
Q7 · Which strategies should be auto-detected vs manually tagged?
Known: the order ticket tags each SIM trade with one of six strategy labels; the analyzer aggregates P&L/win-rate by tag and category. Auto-detection (e.g., pairing long-YES/long-NO as a hedge, or same-ticker opposite-side as a scalp) is feasible from the ledger alone. Missing: your definitions (what counts as “hedge” vs “arbitrage” for you; whether cross-event pairs should link). Discover: place 20–30 SIM trades with manual tags, export JSON, and see which rules would reproduce your tags. Decision needed: codify detection rules (S6).
Q8 · How long should price history be retained?
Known: in-page samples persist in browser localStorage (capped, oldest-first eviction); official candlesticks provide server-side history for longer windows (candlesticks endpoint). Demo historical depth may be limited. Missing: whether you need durable cross-day archives for research (localStorage is per-browser and can be cleared). Discover: decide research needs, then S5 (scheduled snapshot archive via GitHub Action) can persist daily snapshots in the repo. Decision needed: enable S5 or keep browser-only history.
Q9 · Do you want alerts (thresholds, settlements)?
Known: nothing alert-related is built yet (S4). Browser notifications need permission; email would need a third-party service. Missing: which events matter enough to alert: price thresholds, order fills, market settlements, rate-limit warnings. Discover: track usage for a week and note what you found yourself refreshing manually. Decision needed: scope of S4.
Q10 · Is GitHub Pages enabled on this repo?
Known: deployment uses the official GitHub Actions Pages flow (GitHub Pages docs) via .github/workflows/deploy.yml. Missing: whether Pages is enabled with “GitHub Actions” as the source (Settings → Pages). If disabled, the deploy action fails — see F8. Discover: Settings → Pages → Build and deployment → Source: “GitHub Actions”. The PR merge record in COORDINATION.md will state the deploy result either way.

B · Suggestions awaiting review — choose the best path before implementation

Each suggestion lists expected impact, effort, the question(s) that gate it, and the first concrete step. Statuses: proposed → review → accepted / deferred. Triage by editing the status or commenting in COORDINATION.md.

S1 · Server-side credential proxy — unlocks REAL demo order execution proposed gated by Q1, Q2
What: a tiny Cloudflare Worker / Vercel function holding demo API credentials as secrets, exposing signed POST /portfolio/orders, GET /portfolio/balance|positions|fills to the site. Why: static sites can’t hold private keys (flagged F1); auth requires Ed25519/RSA signing per official docs. Impact: replaces the SIM portfolio with real demo fills; enables real P&L tracking. Effort: ~½ day. First step: create demo API key (Q1).
S2 · WebSocket-first market data proposed
What: subscribe to the official demo WS (wss://external-api-ws.demo.kalshi.co/trade-api/ws/v2, endpoint docs) for ticker + orderbook channels; keep REST polling as fallback (already implemented). Why: true real-time updates, far fewer REST calls, respects rate limits (rate limit docs). Impact: smoother charts, more reliable depth. Effort: ~2 h. First step: capture one live WS session and confirm subscribe-message shape (flagged F9).
S3 · Backtesting module on official candlesticks proposed
What: strategy backtests (momentum/mean-revert on YES price) over GET /markets/{ticker}/candlesticks history with the official fee formula applied. Why: lets you compare strategy candidates before risking demo capital; data is official, not synthetic. Impact: better strategy selection. Effort: ~1 day. First step: confirm demo candlestick depth for target series (Q8).
S4 · Alerts proposed gated by Q9
What: browser notifications on price thresholds, fills, and settlements. Why: removes manual refresh loops while tracking live events. Impact: faster reactions. Effort: ~2–4 h. First step: define the alert list (Q9).
S5 · Scheduled snapshot archive proposed gated by Q8
What: nightly GitHub Action (cron) fetching open/settled markets for the 5 topics into data/snapshots/YYYY-MM-DD.json — durable, reviewable history. Why: localStorage is ephemeral; archived snapshots make resolution analytics and drift analysis possible. Impact: enables longitudinal analysis. Effort: ~2 h. First step: approve (Q8) — note the sandbox network restriction (F2) may require running the fetch elsewhere.
S6 · Strategy auto-detection + significance guard proposed gated by Q7
What: codify tag rules (hedge = opposite sides same event; scalp = rapid opposite trades same ticker; momentum = entries after ≥5¢ moves…) and suppress win-rate claims below a minimum sample size. Why: the analyzer currently warns that small samples aren’t significant; codified rules + a minimum-N guard prevent false conclusions. Impact: trustworthy strategy analytics. Effort: ~½ day. First step: review your 20–30 tagged SIM trades (Q7).
S7 · Saved dashboard preferences accepted (implemented: topic filter, time window, live toggles persist per browser)
Kept minimal intentionally; further persistence (columns, density) can follow demand. Decision needed: none — shipped; provide feedback after use.
S8 · Production read-only toggle proposed gated by Q5
What: a clearly-labeled switch to view the same tables against production endpoints (read-only, no keys) alongside demo. Why: demo lineups can be sparse; production context improves decision quality. Impact: better topic coverage. Effort: ~2 h. First step: confirm you want production data visible (Q5).
S9 · Rate-limit budget meter deferred
What: show remaining read/write budget via account/limits (authenticated). Deferred until S1 exists; the public dashboard already self-throttles (120 ms between calls) and polls on fixed schedules.
S10 · This page as the review workflow accepted (shipped)
Suggestions carry status pills; decisions get logged in COORDINATION.md with date + rationale. Review by editing statuses there or requesting changes on the integration PR.
